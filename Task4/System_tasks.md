## 1. АБС и ABS Adapter API — T1

- определить источник истины и таблицы/PL-SQL-процедуры для утверждённых ставок;
- определить правила публикации версии и дату начала действия;
- реализовать версионированный endpoint чтения депозитных продуктов и ставок;
- запретить потребителям прямой доступ к Oracle;
- реализовать техническую аутентификацию и авторизацию сервиса интеграции;
- добавить audit вызовов и correlation ID;
- обеспечить идемпотентную выдачу версии;
- подготовить OpenAPI-контракт и контрактные тесты;
- проверить, что запросы не влияют на платежи и текущие счета.

**Критерий готовности:** сервис интеграции получает утверждённую версию ставок через контролируемый API, а прямое подключение к таблицам Oracle не используется.

## 2. Сервис интеграции депозитов — T1, T2

- реализовать Rates Sync Worker;
- реализовать проверку схемы и бизнес-инвариантов входных данных;
- создать PostgreSQL-схему версий ставок и статусов доставки;
- реализовать Rates API `/api/v1/deposit-rates`;
- возвращать `versionId`, `effectiveFrom`, `generatedAt` и `stale`;
- реализовать File Export Worker;
- формировать CSV и manifest;
- вычислять SHA-256;
- реализовать загрузку `.part` и атомарное переименование;
- обеспечить retry, идемпотентность и ручной повтор публикации;
- добавить метрики, audit и alerts;
- подготовить OpenAPI, JSON Schema/CSV schema и runbook.

**Критерий готовности:** одна подтверждённая версия доступна через REST и опубликована на SFTP с одинаковым `versionId`.

## 3. SFTP и инфраструктура банка — T3

- развернуть SFTP в выделенной зоне обмена с внешними партнёрами;
- создать отдельного пользователя партнёра;
- включить аутентификацию только по SSH-ключу;
- настроить chroot и права только на чтение итоговых файлов;
- запретить shell-доступ;
- настроить IP allowlist при наличии фиксированных адресов партнёра;
- настроить ротацию ключей и процедуру отзыва;
- настроить резервное копирование конфигурации и очистку старых файлов;
- подключить журналирование входов, скачиваний и ошибок;
- настроить мониторинг диска, доступности и сертификатов/ключей.

**Критерий готовности:** партнёр видит только свой каталог, может скачать итоговый файл и не может изменить или удалить его.

## 4. Система кол-центра банка — T4, T5

### Backend Spring Boot

- реализовать клиент Rates API;
- добавить service-to-service authentication;
- настроить таймауты и ограниченные retry только для безопасных GET-запросов;
- валидировать ответ по контракту;
- не обращаться напрямую к АБС;
- при ошибке показывать последнюю локально сохранённую версию с предупреждением;
- логировать correlation ID и номер версии;
- добавить метрики ошибок и времени ответа.

### Frontend React

- добавить экран или блок «Депозитные продукты»;
- показывать продукт, срок, сумму, ставку и ограничения;
- показывать `versionId` и время актуальности;
- явно предупреждать об устаревшей версии;
- реализовать фильтры и сортировку;
- добавить доступность с клавиатуры и масштабирование текста;
- подготовить UI и E2E-тесты.

**Критерий готовности:** оператор получает актуальные ставки в существующем интерфейсе без ручного Excel-файла.

## 5. Система партнёрского кол-центра — T6

- реализовать планировщик проверки новых manifest-файлов;
- подключаться к SFTP по выделенному SSH-ключу;
- скачивать только завершённые версии;
- проверять `schemaVersion`, `versionId`, размер и SHA-256;
- выполнять идемпотентный импорт;
- не активировать новую версию при ошибке валидации;
- сохранять последнюю успешную версию и историю импортов;
- показывать оператору номер версии и время актуальности;
- отправлять техническое подтверждение импорта согласованным способом либо предоставлять отчёт для сверки;
- настроить alerts на отставание и ошибки импорта.

**Критерий готовности:** новая версия автоматически появляется у операторов партнёра, а повреждённый или повторный файл не нарушает текущие данные.

## 6. Сквозные работы — T7, T8, T9

- согласовать владельца данных и процесс утверждения ставок;
- согласовать SLA, допустимую свежесть, RTO и RPO;
- провести threat modelling;
- выполнить security review API и SFTP;
- подготовить contract, integration, performance и failover tests;
- проверить сценарии недоступности АБС, API, SFTP и системы партнёра;
- провести пилот на ограниченной группе операторов;
- подготовить инструкции поддержки и план отката;
- выполнить промышленный запуск и усиленный мониторинг после релиза.
