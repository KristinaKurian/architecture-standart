### **Решение**

Выбрана гибридная схема распространения ставок:

- **внутренний кол-центр** получает актуальные ставки через HTTPS REST API;
- **партнёрский кол-центр** получает версионированный CSV-файл через SFTP;
- **АБС** остаётся источником истины;
- используется уже введённый в задании 3 **Сервис интеграции депозитов / ABS Adapter API**, чтобы не создавать вторую независимую точку доступа к АБС;
- локальная база сервиса хранит подтверждённые версии, историю публикаций, состояние доставки и аудит.

#### API внутреннего кол-центра

Предлагаемый контракт:

```http
GET /api/v1/deposit-rates?productType=deposit&actualAt=2026-08-04
```

Пример ответа:

```json
{
  "versionId": "rates-2026-08-04-01",
  "effectiveFrom": "2026-08-04T00:00:00+03:00",
  "generatedAt": "2026-08-04T00:05:12+03:00",
  "stale": false,
  "products": [
    {
      "productCode": "DEP-12M",
      "name": "Депозит на 12 месяцев",
      "currency": "RUB",
      "termDays": 365,
      "minimumAmount": 100000,
      "annualRate": 15.2
    }
  ]
}
```

API не рассчитывает персональную ставку клиента и не раскрывает данные клиента. Оно предоставляет только утверждённые условия продуктов.

#### Формат файла для партнёра

Файл ставок:

```text
rates_<versionId>.csv
```

Обязательные поля:

```text
version_id,effective_from,product_code,product_name,currency,
term_days,minimum_amount,annual_rate
```

Manifest:

```json
{
  "schemaVersion": "1.0",
  "versionId": "rates-2026-08-04-01",
  "generatedAt": "2026-08-04T00:05:12+03:00",
  "fileName": "rates_rates-2026-08-04-01.csv",
  "recordCount": 8,
  "sha256": "<checksum>"
}
```

Сначала файл загружается с расширением `.part`. После успешной передачи выполняется переименование в итоговое имя, затем публикуется manifest. Партнёр импортирует только файл, для которого присутствует завершённый manifest.

#### Логика выбора технологий

1. **REST API для внутреннего кол-центра.** Система кол-центра развёрнута внутри банка, имеет backend на Spring Boot и допускает расширение. API обеспечивает актуальные данные по запросу и понятную обработку ошибок.
2. **SFTP для партнёра.** Партнёр является внешней организацией, а его интеграционные возможности не описаны. SFTP снижает связность и не требует публиковать внутренний банковский API во внешнем контуре.
3. **PostgreSQL для локального хранилища.** Технология уже используется в банке. Хранилище отделяет чтение ставок кол-центром от доступности и нагрузки АБС.
4. **Фоновые workers.** Синхронизация с АБС и выгрузка файлов выполняются асинхронно, чтобы сбой внешнего канала не блокировал API.
5. **Версии и контрольные суммы.** Позволяют определить актуальность данных, повторно выполнить доставку и обнаружить неполный или повреждённый файл.

#### Согласованность данных

Используется модель eventual consistency. АБС публикует подтверждённую версию, после чего сервис интеграции распространяет её потребителям. До завершения доставки предыдущая версия остаётся доступной. В каждой системе отображается `versionId` и `effectiveFrom`, что позволяет обнаруживать рассинхронизацию.

#### Отказоустойчивость

- при недоступности АБС используется последняя подтверждённая версия;
- при ошибке SFTP публикация повторяется с тем же `versionId`;
- итоговые файлы не перезаписываются частично;
- неуспешные версии попадают в ручной разбор после исчерпания повторных попыток;
- сопровождение видит отставание внутреннего и партнёрского каналов отдельно.

### **Альтернативы**

#### 1. Прямой доступ систем кол-центров к Oracle АБС

Отклонено.
Решение создаёт сильную связанность, повышает нагрузку на АБС, нарушает ограничение на прямой доступ к БД и открывает внешнему партнёру критический банковский контур.

#### 2. Использование только SFTP для обоих кол-центров

Отклонено.
Для внутреннего кол-центра файловая интеграция ухудшает актуальность данных, усложняет пользовательский сценарий и не использует возможности существующего Spring Boot backend.

#### 3. Использование REST API для обоих кол-центров

Отклонено для MVP.
Потребовалось бы публиковать API во внешнем контуре, организовывать внешний IAM, сетевую связность и сопровождение интеграции партнёра. Интеграционные возможности внешней системы в условии не определены.

#### 4. Отправка ставок по email в Excel

Отклонено.
Это сохраняет ручной процесс, не обеспечивает контроль версии, аудит доставки, автоматическую проверку и гарантированную актуальность.

**Недостатки, ограничения, риски**

| Риск или ограничение | Последствие | Снижение риска |
|---|---|---|
| Eventual consistency | Некоторое время кол-центры могут использовать разные версии | Показывать `versionId`, `effectiveFrom`, контролировать lag и задавать допустимое время рассинхронизации |
| Ошибка или задержка импорта партнёром | Операторы партнёра продолжают видеть старые ставки | Manifest, checksum, мониторинг последней выгрузки и операционная процедура подтверждения импорта |
| Компрометация SSH-ключа | Несанкционированное чтение файлов | Отдельный ключ, IP allowlist, chroot, read-only, ротация и отзыв ключа |
| Несовместимое изменение CSV или API | Ошибка отображения или импорта | `schemaVersion`, версионирование API, backward compatibility и contract tests |
| Недоступность АБС | Невозможно получить новую версию | Последняя подтверждённая версия, retry, alert и ручная публикация после восстановления |
| Ошибка в ставках в источнике | Некорректные условия распространятся во все каналы | Процесс утверждения в АБС, audit, версия и возможность быстро отозвать версию |
| Разрастание ответственности сервиса интеграции | Сложный в сопровождении компонент | Разделить API, sync и export на отдельные процессы, сохранять единый домен и контракты |
| Предварительные SLA не согласованы | Решение может не соответствовать ожиданиям бизнеса | Согласовать SLA, RTO/RPO и допустимую свежесть до начала нагрузочного тестирования |
