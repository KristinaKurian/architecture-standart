### <a name="_qmphm5d6rvi3"></a>**Решение**

Предлагаю создать отдельную **систему онлайн-открытия депозитов**, которую сайт и интернет-банк используют через версионируемый HTTPS/REST API. Новая система выпускается независимо от ядра интернет-банка и не получает прямой доступ к таблицам Oracle АБС.

#### Диаграмма контекста C4

Редактируемый файл: [online_deposits_c4.drawio](online_deposits_c4.drawio).

На контекстной диаграмме показаны пользователи, существующие онлайн-каналы, новая система, АБС, система кол-центра и СМС-шлюз. В MVP сотрудник депозитного бэк-офиса продолжает обрабатывать заявку в АБС.

#### Диаграмма контейнеров C4

Редактируемый файл: [online_deposits_c4.drawio](online_deposits_c4.drawio).

Обе страницы находятся в одном редактируемом файле [`online_deposits_c4.drawio`](online_deposits_c4.drawio).

#### Основные контейнеры

| Контейнер | Ответственность | Технология |
|---|---|---|
| Deposit Application API | Приём заявок, валидация, авторизация, идемпотентность, выдача каталога и статусов | Java, Spring Boot |
| Application Database | Заявки, статусы, история, аудит, idempotency keys, кэш продуктов и transactional outbox | PostgreSQL |
| Integration Worker | Надёжная доставка заявок, retry/backoff, ограничение нагрузки, сверка зависших операций | Java, Spring Boot |
| ABS Adapter API | Единственная контролируемая точка интеграции с АБС; вызов разрешённых процедур и представлений | Java, Spring Boot + PL/SQL |
| Notification Worker | Независимая отправка СМС-кодов и статусных уведомлений | Java, Spring Boot |
| Observability | Логи, метрики, аудит, alerts и сквозная трассировка | Конкретный стек определяется IT банка |

#### Логика принятия решения

1. **Отдельная система вместо доработки ядра интернет-банка.** Это снижает зависимость от подрядчика и позволяет выпускать депозитную функциональность отдельно.
2. **Контролируемый адаптер к АБС.** Только ABS Adapter API вызывает разрешённые процедуры или представления АБС. Другие системы не подключаются к таблицам Oracle.
3. **Transactional Outbox.** Заявка и интеграционное задание сохраняются атомарно в PostgreSQL. Worker повторяет временные ошибки и переводит исчерпанные операции в ручной разбор.
4. **Асинхронная обработка интеграций.** Пользователь быстро получает ID заявки, а передача в АБС, кол-центр и СМС выполняется независимо. Это изолирует АБС от пиков пользовательской нагрузки.
5. **Идемпотентность.** Уникальный idempotency key защищает создание заявки, а applicationId используется при всех повторных вызовах АБС.
6. **Поддерживаемый стек.** Java/Spring Boot согласуется с имеющимися в банке Java-компетенциями, а PostgreSQL уже используется в текущем IT-ландшафте.
7. **Путь к целевому состоянию.** После MVP можно добавить версионируемый модуль расчёта ставок, автоматические проверки и формирование договора без изменения внешних API.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### 1. Доработать интернет-банк и сохранить прямой доступ к Oracle

Преимущество — минимальное количество новых компонентов.
Недостатки — усиление связи с legacy-монолитом и подрядчиком, риск влияния на платежи, невозможность надёжно изолировать нагрузку и нарушение ограничения на прямой доступ к БД. Альтернатива отклонена.

#### 2. Создать отдельный сервис, но вызывать АБС синхронно

Преимущество — более простая реализация.
Недостатки — доступность подачи заявки зависит от АБС, при timeout результат операции может быть неопределённым, а пиковая нагрузка напрямую передаётся в Oracle. Альтернатива отклонена.

#### 3. Сразу внедрить брокер сообщений и полностью событийную архитектуру

Преимущества — масштабируемость и удобное подключение новых потребителей.
Недостатки — новая инфраструктура, дополнительные эксплуатационные риски и риск не уложиться в срок MVP.
Вариант можно рассмотреть позднее при подтверждённой нагрузке или появлении корпоративной платформы сообщений.

#### 4. Использовать систему кол-центра как основную систему хранения заявок

Преимущество — часть необходимой CRM-функциональности уже существует.
Недостатки — система принадлежит платформе подрядчика, используется банком только как кол-центр и не должна становиться владельцем банковского процесса открытия продукта. Альтернатива отклонена.

**Недостатки, ограничения, риски**

- Появляется новая PostgreSQL база данных и несколько независимо развёртываемых контейнеров.
- Между новой системой и АБС используется eventual consistency: клиент может некоторое время видеть последний подтверждённый статус.
- Требуется разработать и согласовать безопасный интерфейс АБС и набор разрешённых PL/SQL операций.
- Необходимо реализовать reconciliation для зависших заявок и несогласованных статусов.
- Сбой после выполнения операции в АБС, но до получения ответа, требует обязательной проверки результата по applicationId.
- Нужны развёртывание, резервирование и проверка переключения новой системы между основным и резервным ЦОД.
- Точные SLA, RTO, RPO, допустимая задержка синхронизации и нагрузочные показатели в исходных требованиях не определены и должны быть согласованы.
- Использование технологии transactional outbox добавляет эксплуатационную сложность: требуется контролировать размер таблицы, блокировки, очистку обработанных записей и dead-letter операции.
- Подрядчики интернет-банка и кол-центра могут ограничить скорость изменения интеграционных контрактов.
- Автоматический расчёт ставки и полное открытие продукта не входят в MVP, но должны быть реализованы без замены выбранной интеграционной модели.
