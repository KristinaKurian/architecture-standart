| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F1     | На сайте должна быть реализована форма подачи заявки на открытие депозита. | MVP |
| F2     | Форма на сайте должна позволять указать Ф. И. О., номер телефона, выбранный депозитный продукт и согласие на обработку персональных данных. | Обязательные поля должны проходить валидацию |
| F3     | После отправки заявки с сайта данные должны передаваться в систему кол-центра. | Оператор должен связаться с потенциальным клиентом |
| F4     | Оператор кол-центра должен видеть данные клиента, выбранный депозит(продукт) и статус заявки. | MVP |
| F5     | В интернет-банке клиент должен видеть доступные депозиты и накопительные счета.  | Должны отображаться актуальные условия |
| F6     | Клиент интернет-банка должен иметь возможность выбрать продукт, сумму, срок и счёт списания. | MVP  |
| F7     | Клиент должен иметь возможность подать заявку на открытие депозита или накопительного счёта через интернет-банк. | В MVP заявку продолжает обрабатывать бэк-офис  |
| F8     | Заявка из интернет-банка должна передаваться в АБС. | Необходимо исключить прямую запись в таблицы БД АБС |
| F9     | Каждой заявке должен присваиваться уникальный идентификатор.    | Идентификатор используется во всех взаимодействующих системах  |
| F10    | Сотрудник депозитного бэк-офиса должен видеть и обрабатывать заявки, поступившие из интернет-банка.  | MVP, используется существующий процесс обработки |
| F11    | Для заявки должны храниться текущий статус и история его изменений.  | Например: создана, на рассмотрении, одобрена, отклонена, исполнена      |
| F12    | Клиент должен получать СМС при изменении статуса заявки. | Используется существующий СМС-шлюз  |
| F13    | Система должна предотвращать повторное создание одной заявки или повторное открытие одного депозита.  | Необходимо обеспечить идемпотентность операций  |
| F14    | В целевом состоянии ставка по депозиту должна рассчитываться автоматически.  | не MVP |
| F15    | В целевом состоянии депозит или накопительный счёт должен открываться автоматически без участия бэк-офиса. | Финальное состояние  |
| F16    | При обращении клиента в отделение сотрудник фронт-офиса должен открывать депозит без обращения к бэк-офису. | Финальное состояние  |
| F17    | Система должна формировать и хранить документы по открытому депозиту.  | Документы должны быть связаны с клиентом и договором  |
| F18    | Действия сотрудников и автоматических систем должны регистрироваться в журнале аудита.  | Необходимо хранить пользователя, время, операцию и результат            |
| U   | Удобство использования (Usability) |              |
| U1     | Интерфейс подачи заявки должен быть понятен пользователю без дополнительного обучения. | Нужно учитывать существующую аудиторию банка старшего возраста |
| U2     | Ошибки заполнения формы должны отображаться рядом с соответствующим полем.  | Сообщение должно объяснять причину ошибки и способ исправления |
| U3     | Перед отправкой заявки клиент должен увидеть итоговые параметры продукта.  | Название, сумма, срок, ставка и счёт списания  |
| U4     | Данные авторизованного клиента должны заполняться автоматически.  | Ф. И. О., телефон и доступные счета не должны вводиться повторно |
| U5     | Клиент должен видеть текущий статус заявки в интернет-банке. | Также следует показывать дату последнего изменения                      |
| U6     | Интерфейс должен поддерживать работу с клавиатуры и масштабирование текста и режим для слабовидящих   | Клиенты различного возраст должны иметь возможость пользоваться системой  |
| U7     | После отправки заявки пользователь должен получить понятное подтверждение.  | Нужно показать идентификатор заявки и дальнейшие действия               |
| R   | Надёжность (Reliability)           |              |
| R1     | Заявка не должна теряться при временной недоступности АБС.      | Требуется повторная отправка после восстановления соединения            |
| R2     | Повторная доставка одного запроса не должна приводить к созданию дубликатов.  | Проверка по идентификатору заявки или ключу идемпотентности             |
| R3     | Сбой отправки СМС не должен отменять успешно созданную заявку.   | СМС должно быть отправлено повторно                                     |
| R4     | После сбоя приложения должны сохраняться заявка и последний подтверждённый статус.   | Требуется персистентное хранение данных                                 |
| R5     | Должна сохраняться возможность переключения интернет-банка на резервный ЦОД.   | Такая возможность уже предусмотрена текущей инфраструктурой         |
| R6     | Должен быть реализован контроль корректности передачи заявок между системами.  | Ошибки интеграции должны регистрироваться и обрабатываться              |
| R7     | Версия правил расчёта ставки и входные параметры должны сохраняться.     | Необходимо для воспроизводимости автоматического расчёта                |
| R8     | Доступность процесса подачи заявки должна контролироваться средствами мониторинга.  | SLA 99.9     |
| P   | Производительность (Performance)   |              |
| P1     | Страница со списком депозитных продуктов должна открываться не более чем за две секунды для 95% запросов.    | Необходимо согласование   |
| P2     | После отправки формы пользователь должен получить подтверждение не более чем за три секунды.  | Без учёта времени доставки СМС  |
| P3     | Заявка должна появляться в системе обработки не позднее одной минуты после отправки.  | Необходимо согласование |
| P4     | Изменение статуса должно передаваться в сервис уведомлений не позднее 30 секунд.  | Не включает задержку телеком-оператора |
| P5     | Рост нагрузки на сайт и интернет-банк не должен нарушать проведение платежей и работу АБС. | Нужны ограничение запросов и управление очередью                        |
| P6     | Система должна поддерживать горизонтальное масштабирование новых компонентов. | Количество экземпляров должно увеличиваться без изменения бизнес-логики |
| S   | Поддерживаемость (Supportability)  |              |
| S1     | Для новых компонентов должна быть подготовлена техническая и эксплуатационная документация.   | Описание архитектуры, API, развёртывания и восстановления |
| S2     | Интеграционные контракты должны быть документированы и версионированы.  |  |
| S3     | Все компоненты должны формировать структурированные логи.  | В логах должен использоваться единый идентификатор заявки               |
| S4     | Для системы должны собираться технические и бизнес-метрики.  | Ошибки, время обработки, количество и статусы заявок    |
| S5     | Для критических ошибок должны быть настроены автоматические оповещения.                                                                     | Ошибки АБС, интеграций, очередей и СМС-шлюза                            |
| S6     | Бизнес-логика должна быть покрыта модульными и интеграционными тестами.  | Тесты должны запускаться в CI/CD                                        |
| S7     | Должны быть подготовлены инструкции по диагностике и восстановлению после сбоев.  |  |
| S8     | Новые компоненты должны использовать технологии, которые может сопровождать IT-команда банка.  | Следует минимизировать зависимость от подрядчиков  |
| S9     | Новая депозитная функциональность должна минимально зависеть от обновления ядра интернет-банка подрядчиком.                                 | Желательно обеспечить отдельный цикл выпуска                            |
| +R  | + Ограничения (Restrictions)       |              |
| +R1    | Интернет-банк на этапе MVP остаётся на ASP.NET MVC 4.5, .NET Framework 4.5 и MS SQL.  | Полная замена платформы не входит в срок шесть месяцев                  |
| +R2    | АБС продолжает использовать Delphi, Oracle и PL/SQL.   | Основная бизнес-логика системы находится в Oracle  |
| +R3    | Сайт продолжает использовать PHP и React.js.   | Сайт является собственной разработкой банка    |
| +R4    | Система кол-центра продолжает использовать React, Spring Boot и PostgreSQL.    | Платформа сопровождается подрядчиком    |
| +R5    | Новые компоненты не должны напрямую изменять таблицы базы данных АБС.    | Требуется контролируемый API или интеграционный слой       |
| +R6    | Существующие платежи и открытие текущих счетов не должны быть нарушены.   | Нужны регрессионные тесты    |
| +R7    | Сотрудники депозитного и кредитного направлений не должны получать доступ к данным друг друга.    | Требование информационной безопасности    |
| +R8    | Доступ сотрудников должен предоставляться на основе ролей.   | Cписок минимально необходимых прав   |
| +R9    | Персональные и банковские данные должны передаваться только по защищённым каналам.  | Для сетевых взаимодействий требуется TLS  |
| +R10   | Персональные данные, пароли и токены не должны записываться в открытом виде в логи.  | Необходимо маскирование чувствительных данных   |
| +R11   | Для каждой заявки должен использоваться единый идентификатор во всех системах.  | Требуется для аудита, диагностики и защиты от дубликатов  |
| +R12   | MVP должен быть реализован в течение шести месяцев.   | Обработка заявок бэк-офисом сохраняется                                 |
| +R13   | Полностью автоматическое открытие депозитов должно быть реализовано в течение одного года.  | Бэк-офис исключается из стандартного процесса                           |
| +R14   | Для уведомлений должен использоваться существующий СМС-шлюз телеком-оператора.   | Необходимо учитывать его временную недоступность                        |
| +R15   | Система должна соответствовать внутренним требованиям банка по информационной безопасности и аудиту операций.  |   |
