# Task2. Требования по модели FURPS+

Значения производительности и доступности, отмечены как предварительные и требуют согласования с бизнесом и с разработкой.

| Код | Требования | Комментарий |
|---|---|---|
| **F** | **Функциональные (Functionality)** | |
| F1 | На сайте должна быть реализована форма подачи заявки на открытие депозита. | MVP |
| F2 | Форма на сайте должна позволять указать Ф. И. О., номер телефона, выбранный депозитный продукт и согласие на обработку персональных данных. | Обязательные поля должны проходить валидацию |
| F3 | После отправки заявки с сайта данные должны передаваться в систему кол-центра. | Оператор должен связаться с потенциальным клиентом. **ASR** |
| F4 | Оператор кол-центра должен видеть данные клиента, выбранный продукт и статус заявки. | MVP |
| F5 | В интернет-банке клиент должен видеть доступные депозиты и накопительные счета. | Условия продуктов должны быть актуальными |
| F6 | Клиент интернет-банка должен иметь возможность выбрать продукт, сумму, срок и счёт списания. | MVP |
| F7 | Клиент должен иметь возможность подать заявку на открытие депозита или накопительного счёта через интернет-банк. | В MVP заявку продолжает обрабатывать бэк-офис |
| F8 | Заявка из интернет-банка должна передаваться в АБС без прямого изменения таблиц базы данных АБС. | Способ интеграции определяется в ADR. **ASR** |
| F9 | Каждой заявке должен присваиваться единый уникальный идентификатор. | Идентификатор используется во всех взаимодействующих системах. **ASR** |
| F10 | Сотрудник депозитного бэк-офиса должен видеть и обрабатывать заявки, поступившие из интернет-банка. | MVP, используется существующий процесс обработки |
| F11 | Для заявки должны храниться текущий статус и история его изменений. | Например: создана, на рассмотрении, одобрена, отклонена, исполнена. **ASR** |
| F12 | Клиент должен получать СМС при изменении значимых статусов заявки. | Используется существующий СМС-шлюз. **ASR** |
| F13 | Система должна предотвращать повторное создание одной заявки и повторное открытие одного депозита. | Необходимо обеспечить идемпотентность операций. **ASR** |
| F14 | В целевом состоянии ставка по депозиту должна рассчитываться автоматически. | Срок — один год; ручной расчёт в Excel исключается. **ASR** |
| F15 | В целевом состоянии депозит или накопительный счёт должен открываться автоматически без участия бэк-офиса. | Финальное состояние. **ASR** |
| F16 | При обращении клиента в отделение сотрудник фронт-офиса должен открывать депозит без обращения к бэк-офису. | Финальное состояние. **ASR** |
| F17 | Система должна формировать и хранить документы по открытому депозиту. | Документы должны быть связаны с клиентом, заявкой и договором. **ASR** |
| F18 | Действия сотрудников и автоматических компонентов должны регистрироваться в журнале аудита. | Необходимо хранить инициатора, время, операцию и результат. **ASR** |
| F19 | Сайт, интернет-банк, отделения и кол-центр должны использовать актуальные условия депозитных продуктов. | Источник условий и ставок должен быть единым либо согласованно синхронизироваться. **ASR** |
| **U** | **Удобство использования (Usability)** | |
| U1 | Пользователь должен иметь возможность самостоятельно заполнить и отправить заявку без обращения в поддержку. | Критерий пользовательского тестирования требует согласования |
| U2 | Ошибки заполнения формы должны отображаться рядом с соответствующим полем. | Сообщение должно объяснять причину ошибки и способ исправления |
| U3 | Перед отправкой заявки клиент должен увидеть итоговые параметры продукта. | Название, сумма, срок, ставка и счёт списания |
| U4 | Данные авторизованного клиента должны заполняться автоматически. | Ф. И. О., телефон и доступные счета не должны вводиться повторно |
| U5 | Клиент должен видеть текущий статус заявки в интернет-банке. | Следует показывать дату последнего изменения |
| U6 | Интерфейс должен поддерживать работу с клавиатурой, масштабирование текста и режим для слабовидящих. | Нужно учитывать основную аудиторию банка старшего возраста |
| U7 | После отправки заявки пользователь должен получить понятное подтверждение. | Нужно показать идентификатор заявки и дальнейшие действия |
| **R** | **Надёжность (Reliability)** | |
| R1 | Заявка не должна теряться при временной недоступности АБС. | Требуется надёжная повторная обработка после восстановления доступности. **ASR** |
| R2 | Повторная доставка одного запроса не должна приводить к созданию дубликатов. | Связано с F13. **ASR** |
| R3 | Сбой отправки СМС не должен отменять успешно созданную заявку. | Основная операция и уведомление должны быть независимы. **ASR** |
| R4 | После сбоя приложения должны сохраняться заявка и последний подтверждённый статус. | Требуется персистентное хранение состояния. **ASR** |
| R5 | Должна сохраняться возможность переключения интернет-банка на резервный ЦОД. | Возможность предусмотрена текущей инфраструктурой. **ASR** |
| R6 | Для каждой передаваемой заявки система должна фиксировать результат доставки и обработки. | Неподтверждённые заявки должны обнаруживаться мониторингом и попадать в повторную обработку или ручной разбор. **ASR** |
| R7 | Версия правил расчёта ставки и входные параметры должны сохраняться. | Необходимо для воспроизводимости автоматического расчёта. **ASR** |
| R8 | Доступность процесса подачи заявки должна контролироваться средствами мониторинга. | Целевой SLA необходимо определить и согласовать; предварительное значение — 99,9%. **ASR** |
| R9 | Система должна обнаруживать заявки с превышенным сроком обработки или несогласованными статусами в разных системах. | Нужен механизм сверки и ручного разбора проблемных заявок. **ASR** |
| R10 | Для процесса подачи и обработки заявок должны быть определены RTO и RPO. | Конкретные значения должны быть согласованы с владельцем бизнеса и с разработкой. **ASR** |
| **P** | **Производительность (Performance)** | |
| P1 | Страница со списком депозитных продуктов должна открываться не более чем за две секунды для 95% запросов. | Предварительное значение, требует согласования. **ASR** |
| P2 | После отправки формы пользователь должен получить подтверждение не более чем за три секунды. | Без учёта времени доставки СМС; требует согласования. **ASR** |
| P3 | Заявка должна появляться в системе обработки не позднее одной минуты после отправки. | Предварительное значение, требует согласования. **ASR** |
| P4 | Изменение статуса должно передаваться в подсистему уведомлений не позднее 30 секунд. | Не включает задержку телеком-оператора; требует согласования. **ASR** |
| P5 | Рост нагрузки на сайт и интернет-банк не должен нарушать проведение платежей и работу АБС. | Архитектура должна изолировать АБС от пиков нагрузки; механизм выбирается в ADR. **ASR** |
| P6 | Новые компоненты должны поддерживать горизонтальное масштабирование. | Состояние не должно зависеть от одного экземпляра приложения. **ASR** |
| **S** | **Поддерживаемость (Supportability)** | |
| S1 | Для новых компонентов должна быть подготовлена техническая и эксплуатационная документация. | Описание архитектуры, контрактов, развёртывания и восстановления |
| S2 | Интеграционные контракты должны быть документированы и версионированы. | **ASR** |
| S3 | Все компоненты должны формировать структурированные логи с единым идентификатором заявки. | Требуется сквозная диагностика. **ASR** |
| S4 | Для системы должны собираться технические и бизнес-метрики. | Ошибки, время обработки, количество и статусы заявок. **ASR** |
| S5 | Для критических ошибок должны быть настроены автоматические оповещения. | Ошибки АБС, интеграций и СМС-шлюза. **ASR** |
| S6 | Критическая бизнес-логика должна быть покрыта модульными, интеграционными и Unit тестами. | Тесты должны запускаться с использованием CI/CD |
| S7 | Должны быть подготовлены инструкции по диагностике и восстановлению после сбоев. | Эксплуатационные runbook |
| S8 | Новые компоненты должны использовать технологии, которые может сопровождать IT-команда банка. | Следует минимизировать зависимость от новых подрядчиков. **ASR** |
| S9 | Новая депозитная функциональность должна выпускаться без обязательного обновления ядра интернет-банка подрядчиком. | Интеграция должна осуществляться через стабильный версируемый контракт. **ASR** |
| S10 | Изменение интеграционного контракта не должно одновременно требовать обновления всех взаимодействующих систем. | Нужны обратная совместимость и контрактное тестирование. **ASR** |
| **+R** | **+ Ограничения (Restrictions)** | |
| +R1 | Интернет-банк на этапе MVP остаётся на ASP.NET MVC 4.5, .NET Framework 4.5 и MS SQL. | Полная замена платформы не входит в срок шесть месяцев. **ASR** |
| +R2 | АБС продолжает использовать Delphi, Oracle и PL/SQL. | Основная бизнес-логика системы находится в Oracle. **ASR** |
| +R3 | Сайт продолжает использовать PHP и React.js. | Сайт является собственной разработкой банка. **ASR** |
| +R4 | Система кол-центра продолжает использовать React, Spring Boot и PostgreSQL. | Платформа сопровождается подрядчиком. **ASR** |
| +R5 | Новые компоненты не должны напрямую изменять таблицы базы данных АБС. | Уточняет F8; способ интеграции определяется в ADR. **ASR** |
| +R6 | Существующие платежи и открытие текущих счетов не должны быть нарушены. | Требуются обратная совместимость и регрессионные тесты. **ASR** |
| +R7 | Сотрудники депозитного и кредитного направлений не должны получать доступ к данным друг друга. | Требование информационной безопасности. **ASR** |
| +R8 | Доступ сотрудников должен предоставляться на основе ролей и минимально необходимых прав. | Требуется RBAC. **ASR** |
| +R9 | Персональные и банковские данные должны передаваться только по защищённым каналам. | Конкретные протоколы определяются архитектурой. **ASR** |
| +R10 | Персональные данные, пароли и токены не должны записываться в открытом виде в логи. | Необходимо маскирование чувствительных данных. **ASR** |
| +R11 | Для каждой заявки должен использоваться единый идентификатор во всех системах. | Связано с F9. **ASR** |
| +R12 | MVP должен быть реализован в течение шести месяцев. | Обработка заявок бэк-офисом сохраняется. **ASR** |
| +R13 | Полностью автоматическое открытие депозитов должно быть реализовано в течение одного года. | Бэк-офис исключается из стандартного процесса. **ASR** |
| +R14 | Для уведомлений должен использоваться существующий СМС-шлюз телеком-оператора. | Нужно учитывать его временную недоступность. **ASR** |
| +R15 | Система должна соответствовать внутренним требованиям банка по информационной безопасности и аудиту операций. | Конкретные внутренние нормативы в условии не приведены. **ASR** |
| +R16 | Новые сервисы и интеграции не должны позволять обходить разделение доступа депозитного и кредитного направлений. | Ограничение должно соблюдаться на уровне ролей, интерфейсов и данных. **ASR** |

## Архитектурно значимые требования

| Требования | Архитектурное влияние |
|---|---|
| F3 | Требуется интеграция сайта с системой кол-центра и контроль доставки заявки. |
| F8, +R5 | Необходимо исключить прямое изменение таблиц БД АБС и определить контролируемый интеграционный контракт. |
| F9, +R11 | Во всех системах должен использоваться единый идентификатор заявки для аудита и сквозной трассировки. |
| F11, R4 | Необходимо персистентно хранить состояние заявки и историю его изменений. |
| F13, R2 | Создание заявки и открытие депозита должны быть идемпотентными. |
| R1, R6, R9 | Заявки не должны теряться; нужны контроль доставки, повторная обработка и сверка зависших заявок. |
| F12, R3, +R14 | Отправка СМС должна быть отделена от основной операции и не должна влиять на успешность создания заявки. |
| F14, R7 | Автоматический расчёт ставки требует версионирования правил и сохранения входных параметров. |
| F15, F16, +R12, +R13 | Архитектура MVP должна поддерживать ручную обработку и не препятствовать полной автоматизации через год. |
| F17 | Требуются формирование, хранение и связь документов с заявкой и договором. |
| F18, +R15 | Все действия пользователей и компонентов должны попадать в защищённый журнал аудита. |
| F19 | Условия депозитных продуктов и ставки должны быть согласованы между всеми каналами. |
| R5, R10 | Решение должно учитывать резервный ЦОД и согласованные параметры восстановления RTO/RPO. |
| P1–P4, R8 | Требуются согласованные показатели времени ответа, доставки и доступности, которые будут проверяться мониторингом. |
| P5 | Новая нагрузка онлайн-каналов не должна влиять на существующие платежи и работу АБС. |
| P6 | Новые компоненты должны допускать горизонтальное масштабирование. |
| S2, S10 | Интеграционные контракты должны быть версионируемыми, обратно совместимыми и проверяться контрактными тестами. |
| S3, S4, S5 | Требуются централизованные логи, метрики, мониторинг и автоматические оповещения. |
| S8, S9 | Технологии должны сопровождаться командой банка, а новая функциональность — минимально зависеть от ядра подрядчика. |
| +R1–+R4 | Архитектура должна учитывать существующие legacy-технологии всех систем. |
| +R6 | Изменения не должны нарушать существующие платежи и открытие текущих счетов. |
| +R7, +R8, +R16 | Требуются разделение полномочий и ролевая модель доступа, не допускающая обхода ограничений. |
| +R9, +R10 | Требуются защищённые взаимодействия и маскирование чувствительных данных. |
